## The finding: fixed args land at the FRONTIER, but CALL reads them at base+1

compileCall (compile.ts:1005) compiles FIXED args via `this.reserve(ctx, 1)`
(allocation frontier) while emitting `CALL A=base B=n+1` (window at base+1).
When base < frontier-1 — a call compiled INTO a pre-reserved window BELOW
the live frontier — the arg is written ABOVE where CALL reads it. Your s5
"below-frontier frontier reset" fix handled the POST-call frontier; the ARG
WINDOW placement is the remaining half.

How a call gets below the frontier: CONCAT operands. The Concat case
(compile.ts:1230) reserves chain.length consecutive regs and compiles each
operand into start+i; flattenConcat (compile.ts:1464) flattens only the LEFT
spine, so RIGHT-nested concat trees (what the M4 parser produces for
`a .. b .. c` — verified via proto dump) compile as nested BinaryExprs,
placing call operands at non-last chain positions, i.e. below the frontier.

## Proposed fix (your call on shape)

In the fixed-args loop, compile each arg INTO the window slot instead of
reserve(1) at the frontier:

```
} else {
  for (let i = 0; i < args.length; i++) {
    const r = argStart + i;
    if (ctx.freeReg < r + 1) ctx.freeReg = r + 1;   // window alignment
    this.compileExpr(ctx, args[i], r, 'single');
  }
  b = args.length + (argStart - base - 1) + 1;
}
```

(At the normal frontier this is byte-identical to today's behavior; below
the frontier it puts the arg where CALL reads it. The SELF path has the
same class of issue: the post-SELFK `reserve(1)` "self slot" assumes
frontier == base+1 — worth sweeping both paths. Separately: consider
flattening right-nested concat trees in flattenConcat — semantically
neutral (nested CONCATs are legal) but it would restore the single-CONCAT
shape PUC emits and your instruction-count parity gate expects.)
