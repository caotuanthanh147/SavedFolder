# DECISIONS-M10 — Payments and webhooks (doc v4 format)

Module M10, decided 2026-10-10 after RESEARCH-M10. Evidence rows cite the research log. Tier numbering follows doc.md "Decision authority".

| # | Decision | Evidence | Tier |
|---|---|---|---|
| D-M10-1 | **D6 resolved: provider-agnostic webhook verifier interface.** `stripe` implementation follows the documented scheme (`Stripe-Signature: t=<unix>,v1=<hex>`; HMAC-SHA256 over `${t}.${rawBody}`; hex; 5-minute default tolerance; accepts any valid v1 for rotation; parses only t=/v1=, ignores other schemes). `custom` provider (dev/test): `X-Event-Id` header + `X-Signature: hex HMAC-SHA256(rawBody, secret)`. Both share one interface. | RESEARCH: docs.stripe.com, webhooks.fyi, bubble.io downgrade note | 1 (D6 was pre-declared Tier-3-blocking; interface approach mirrors M9's D5) |
| D-M10-2 | **Idempotency = insert-first gate on UNIQUE(provider, event_id).** Duplicate deliveries return the stored outcome (200, `duplicate: true`), never re-issue a key. | RESEARCH: hookdeck, hubspot, dev.to at-least-once delivery | 1 |
| D-M10-3 | **Event vocabulary mapped per provider.** stripe: `checkout.session.completed` → payment confirmed, `charge.refunded` → refund, `charge.dispute.created` → chargeback (fraud-shaped: revokes + blacklists the order's discord_id). custom: `payment.confirmed`, `payment.refunded`, `payment.disputed`. Unknown event types: 200 + `ignored` (provider best practice — do not force redelivery storms) + event row for the audit trail. | RESEARCH: stripe-events gist, docs.stripe.com | 1 |
| D-M10-4 | **Key issuance reuses the M9 tier-key path**: full keys row + key_scripts entitlements + audit entry + plaintext returned once in the webhook response (for DM/email delivery). `created_by = "m10:<provider>"`. Product row supplies tier/days/scripts. | M9 precedent (freekey.ts issuance), §17 | 1 |
| D-M10-5 | **Refunds revoke; blacklist is conditional**: product row `refund_blacklists` flag (default 0) for refunds; disputes always blacklist kind `discord` (chargebacks are fraud-shaped). Blacklist value hashed like all other blacklist entries (sha256 of raw id). | §17 "optionally blacklist" | 1 |
| D-M10-6 | **New tables `orders`, `payment_products`, `payment_events` are M10-applied additive tables** (clearly marked, `CREATE TABLE IF NOT EXISTS` in payments.ts) until the owner rules on CCP-4; M2's db/ migrations untouched. | CCP-3 precedent (dash_totp), §6 has no orders table | 3 (CCP-4 filed) |
| D-M10-7 | **Reconciliation report** = `/admin/payments/reconcile` (owner/admin token): compares orders table against keys: (a) orders with status=paid whose key is missing/revoked, (b) refunded/disputed orders whose key is still active, (c) keys created by m10 with no order row. Live provider fetch is env-gated (PAYMENTS_PROVIDER_BASE + provider API secret); without it the report covers the local table (b/c classes + a=0) and says so. | §17 line 4; RESEARCH reconciliation patterns | 1 |
| D-M10-8 | **Webhook endpoint = `POST /webhooks/payments/:provider`**, unauthenticated by admin token (signature IS the auth), but rate-limited per IP + strict body-size limit (256 KB) + raw-byte signature (no re-serialization). Malformed JSON → 400 + event row. Signature fail → 400 `invalid_signature` (no event detail leak). | §18 strict input validation; RESEARCH raw-body note | 1 |
| D-M10-9 | **Amount recorded verbatim** (`amount_minor`, `currency` passthrough); no fee math in M10 (provider dashboard owns fees). | RESEARCH fees note | 1 |
| D-M10-10 | **Delivery target captured from event metadata** (`discord_id` or `email` from checkout custom fields / custom provider fields), stored on the order, and echoed in the issuance response — actual DM/email sending is M8 (bot) / M12 (ops) territory, NOT-RUN here. | §17 "deliver by DM or email"; module boundaries | 1 |
