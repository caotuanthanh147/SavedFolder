# DECISIONS-M13 — Decision Log (doc.md "Decision authority", v4/18555ec format)

All decisions below follow doc.md's three-tier model. Evidence rows refer to
RESEARCH-M13.md. Tier 3 issues found: none requiring a Contract Change
Proposal; one interface convention (D-M13-6) is Tier 2 and msg'd to the M3
owner.

| # | Decision | Options considered | Choice | Why (with evidence) | Tier | Reversibility | Affects modules |
|---|----------|--------------------|--------|---------------------|------|---------------|-----------------|
| D-M13-1 | Module home for the init packaging pipeline | `loader/stub/` (with the stub generator) vs `tools/` (doc's "build scripts" bucket) | **`loader/stub/`** | The packager and the generator are one pipeline (package → build id → stub embeds build's size+hashes); splitting them forces a cross-package import for `InitBuild`. `tools/` stays for watermark extractor per the doc layout | 1 | high (move folder + fix imports) | none |
| D-M13-2 | Init build identity / cache-busting | sequential build numbers vs content-addressed id (`b` + sha256 prefix) | **content-addressed: `"b" + sha256[0:12]`** | Content addressing makes the URL itself the cache-buster: new init content → new URL → old cached responses stay valid forever (`immutable`, MDN) with zero invalidation logic; Cloudflare request collapsing covers cold-build bursts (RESEARCH: CF cache docs). 12 hex chars = 48 bits — collision odds negligible at this scale and a collision is caught by size+hash mismatch (stub refuses to run) | 1 | high (build ids are internal + DB `script_versions.init_build`) | M1 (stores init_build), M3 (init uploads flow through packageInit) |
| D-M13-3 | How `/static/init_<build>.lua` gets CDN caching | (a) R2 custom domain + Cache Rule vs (b) Worker route + `caches.default` Cache API vs (c) Workers Static Assets | **(b) Worker + Cache API** | `.lua` is NOT in Cloudflare's default cached-extension list (RESEARCH: default-cache-behavior) — option (a) silently does not cache without an extra Cache Rule; option (c) is deploy-time-only while init builds upload at runtime via admin API. (b) works regardless of extension, needs no external config, M1 already owns the hostname. Route handlers accept an injected `edgeCache` (interface `match/put`); M1 adapts `caches.default` | 2 | high (swap the injected cache; headers unchanged) | M1 (mounts `handleGetInit`, adapts caches.default), M12 (ops: scale-out = option (a) later) |
| D-M13-4 | On-disk cache location (Open Decision D12, first half) | executor-root vs shared folder vs per-script folder | **workspace-relative folder `lp/`, file `lp/init_<build>.lua`, folder name configurable at stub generation** | Executor FS APIs are workspace-relative (Potassium docs). Content-addressed filenames are collision-free across scripts and dedupe naturally when scripts share an init build; old builds orphan harmlessly (stub only reads its own build). Configurable constant (not a fixed contract) lets the platform rename later without contract change | 2 | high (new stubs carry the new name; old caches re-download once) | M3 (init may document the cache dir), M12 (ops) |
| D-M13-5 | Cache validation algorithm (Open Decision D12, second half) | (a) FNV-1a32+size vs (b) FNV-1a32+DJB2+exact size vs (c) SHA-256+size | **(b)** | Dual 32-bit hashes = 64-bit fingerprint at ~285 ns/byte vs SHA-256's ~936 ns/byte (local benchmark, RESEARCH) and ~25 lines of Lua vs ~5KB embedded in every per-fetch stub; (a) is weaker against same-size tampering for marginal savings. Unkeyed hashes only filter corruption/casual tampering — real trust anchors are server-side (doc §3 "client code is never trusted", §5.2 x-proof philosophy). bit32 (Luau builtin) gates FNV; DJB2 needs no bit ops so validation still works without bit32 | 2 | high (expected values are per-stub; algorithm swap = template change) | M3 (may reuse the same primitives for stub-side checks) |
| D-M13-6 | Stub→init handoff convention | (a) globals set by stub vs (b) init chunk returns entry function called with payload table vs (c) side file | **(b): stub does `local entry = loadstring(data)(); entry(payload)` with payload `{api, script_id, build, t, s, r}`** | No global pollution; explicit, testable contract; per-fetch data (§5.6: fetch time, stub id, build id, per-stub random) and the bases the init needs for `/auth` flow in one table. `api`/`script_id` are required by the init's own auth calls (§5.5), `build` by the auth request body, `t/s/r` = the per-fetch data block | 2 | medium (both stub and init change together; M3 has not shipped its init yet — msg'd) | **M3 (glm1)** — init must return an entry function accepting this payload |
| D-M13-7 | Cache-write behavior when the executor FS is unavailable or fails (Open Decision D12, third half) | refuse to run vs run without cache | **best-effort write, always run** | Availability over cache persistence: the init bytes were already validated this session; a failed `writefile` only costs a re-download next session. `pcall` guards every FS call (Potassium docs: readfile errors on missing; write semantics undocumented for failures). Harness scenario `write-fail` proves the path | 2 | high | none |
| D-M13-8 | Response headers | which cache-control per endpoint | **stub: `no-store` (unique per fetch, §5.6 "unique per fetch"); init: `public, max-age=31536000, immutable`; all 4xx/5xx: `no-store`** | Uniqueness is the stub's anti-save property — no layer may cache it (CF docs: no-store never cached). Init builds are immutable by construction (D-M13-2). Negative responses get `no-store` so a transient miss does not poison the edge (CF caches some error codes by default) | 2 | high | M1 (mounts handlers as-is), M12 |
| D-M13-9 | Stub size/hash embedding source | separate manifest file on CDN vs compute from served bytes at generation time | **compute from the actual init bytes at stub generation** | The generator hashes the very bytes `getInitBytes` will serve — no manifest store to keep consistent, no schema addition; M1's existing `script_versions.init_build` lookup + blob read is enough. (A per-isolate memo of the hash triple is M1's optimization option, noted in README) | 1 | high | M1 (one blob read per stub fetch, or memoize) |
| D-M13-10 | `request()` response acceptance criteria | trust `Success` only vs also require status + type checks | **`Success == true` AND `StatusCode == 200` AND `type(Body) == "string"` AND validation** | UNC docs define the response shape but executor quirks exist; the body hash+length check is the real gate, the shape checks prevent weird responses from reaching it. Generic failure on any miss (§8 rules: generic messages) | 1 | high | none |
